### Notes (rechecks and auditor findings)

- **BR-4 — confirmed defect (probe run outside the repo).** `P/vo.go:27` bounds `dollars > (1<<63-1)/1e9` but then adds the fraction, so `dollars == 9223372036` with a fraction above `.854775807` overflows silently: `NewCostVo("9223372036.9")` returns **no error**, `Nanodollars() = -9223372036809551616`, `String() = "-9223372036.-809551616"`. Unreachable in normal use but it reports a wrong amount instead of refusing. `P/vo_test.go:37` only tests `99999999999.0` (well past the bound), so the boundary is untested.
- **BR-4 / BR-10 — exponent notation.** `P/vo.go:20-22` rejects `1e-7`/`5E-7` (and `P/vo_test.go:37` pins `1e-3` as invalid). Claude Code is a Node program; `JSON.stringify` writes numbers below 1e-6 in exponent form. A real non-zero cost below a millionth of a dollar would make `newResultPayload` fail (`I/result_payload.go:36-39`) and `Ask` would discard a **successful** reply as `UnreadableReplyError` (`I/claude_code_proxy.go:125-126`). Low likelihood; flagged as a risk, not counted.
- **AC-18 / BR-8 / NFR-2 — redaction is not tested along the path that matters.** The only test is `Credential.Redact` on a string. Nothing proves that Claude's explanation containing the pass comes out of `Ask` as a redacted `ProblemError`. Also, redaction runs on the **raw JSON** before decoding (`I/claude_code_proxy.go:177`). A secret containing a character that JSON escapes (`"`, `\`, control characters, or one Claude Code writes as `\uXXXX`) would not match, and would reappear after decoding in `ProblemError.Explanation` or `ResultDto.Text`. Real `sk-ant-…` tokens are URL-safe, so the risk is low today. A robust fix would also redact the decoded fields. Under `.claude/rules/testing.md` a pure-function test is possible if redaction and decoding are composed somewhere other than the process I/O. As written they are joined only inside `execute`/`Ask`, so the scenario can't be unit-tested without a fake CLI.
- **BR-10 — identity is not removed.** `UnreadableReplyError.Output` (`I/claude_code_proxy.go:126`) and `ProblemError.Explanation` only hide the secret. The previous iteration's NFR (`.sdd/2026-11-26-cli-auth-profiles/PRD.md:297`: "Account identity details (email, organisation) … never included in failures") is applied to `ReadStatus` (`I/claude_code_proxy.go:74`, `statusAnswer.WithoutIdentity`) but not to `Ask`. This PRD does not restate that rule. Whether it carries over is a James decision.
- **AC-17 / NFR-1 — child processes.** `exec.CommandContext` kills only the direct Claude Code process (`I/claude_code_proxy.go:151-154`). No process group is set, so commands Claude started through its Bash tool can outlive the give-up. `WaitDelay` then stops waiting on their pipes after 0.5 s. "Claude Code stops" holds for the main process only. Nothing measures the library's added overhead. The give-up test reads `cancelledAt` from another goroutine without synchronisation (a data race under `-race`).
- **AC-12 — unclear, depends on Claude Code.** The code passes `--resume` and reports whatever `session_id` Claude Code returns. The reference only stays the same if Claude Code 2.1.x keeps the session ID on `-p --resume`. Only the live test (not run here) can show that.
- **AC-16 — unclear, depends on Claude's wording.** The check depends on the exact phrase "Not logged in" (a known risk in PRD §7). The recorded 2.1.332 answer is decoded correctly. If Claude Code reports a signed-out person on stderr with no JSON, the result is `UnreadableReplyError`, not "not signed in".
- **AC-5 — recheck.** `I/query_command_test.go:17-21` asserts the exact argument list with `MaxTurns: 0`, so it does pin "no `--max-turns`". Its name and intent are about the prompt, not the cap, which is why Jev read it as no-test. Nothing tests the absence of a cap explicitly.
- **BR-9 — achievable test.** Mirror `test/auth_test.go:132` (copy the real `claude` executable, `WithCLIPath`, delete it, then call `Query().Ask`). This uses no fake CLI. Separately, a work folder deleted between the `os.Stat` (`:109`) and the run makes `chdir` fail with ENOENT. That matches `fs.ErrNotExist` at `:170` and is misreported as "Claude Code is not installed" (a race-only misclassification).
- **Safety note on integration tests:** `T:49-59` (unknown conversation) and `T:61-69` (unavailable model) are not gated by `GO_CLAUDE_LIVE_TESTS` and use the everyday sign-in. The unavailable-model test reaches the API; the recorded cost is 0.
